# Stage: Persist Speaker Aliases Across Launches

## Goal
Persist diarization speaker aliases in the macOS app so a user’s manual alias mappings survive app restarts and automatically reappear in the Speaker aliases editor when Canary Transcriber launches again. Keep the existing TextEditor-based manual workflow unchanged; this stage only adds lightweight persistence and UI hydration around the current alias format.

## Scope
- Persist the speaker alias editor content locally on the Mac using standard macOS app storage.
- Load the saved alias text back into the SwiftUI editor on app launch before the user starts a new transcription.
- Keep the current manual alias editor, parsing logic, and export behavior intact.
- Ensure the persisted aliases continue to be used when building diarization config for transcription runs.
- Do not introduce account sync, cloud storage, or a new alias management screen.
- Do not change diarization labeling semantics beyond restoring the user’s saved mappings.

## Success Criteria
- If a user enters alias mappings such as `SPEAKER_00 = Alice`, quits the app, and relaunches it, the same mappings are visible in the Speaker aliases editor.
- Saved aliases are available for the next transcription run without requiring re-entry.
- Clearing the editor and saving/closing the app results in an empty editor after relaunch.
- The implementation uses a minimal, sandbox-safe macOS persistence mechanism that fits the current SwiftUI app, preferably `@AppStorage`/`UserDefaults` for the editor text.
- Existing diarization transcription output continues to honor the alias map exactly as before.
- `swift build --product canary-transcriber` still succeeds after the change.

## Constraints
- Keep the current manual alias editor UI and line-based `SPEAKER_XX = Name` format.
- Prefer a low-risk solution with no custom database, no file picker, and no extra dependencies.
- Persist only local app state; do not require network access or external services.
- Avoid breaking existing saved transcripts or the current parser that ignores blank lines and comments.
- The solution should fit the existing single-window SwiftUI architecture in `Sources/CanaryTranscriber/main.swift`.

## Risks
- Saving the raw editor text can preserve accidental formatting mistakes, malformed lines, or stale aliases until the user edits them.
- If persistence is wired incorrectly, the editor may not hydrate before the first render or may overwrite user changes on launch.
- Migrating from a transient `@State` field to stored state can create subtle SwiftUI update loops if save/load logic is placed in the wrong lifecycle hook.
- A simple string-only store does not provide schema validation, so future alias-format changes may require migration.

## Dependencies
- SwiftUI state management in `Sources/CanaryTranscriber/main.swift`.
- macOS `UserDefaults` / `@AppStorage` for local persistence.
- Existing `speakerAliasesText` parsing and alias injection into the diarization batch config.
- Current app launch flow and `ContentView` lifecycle (`.onAppear` / state initialization).
